--- FRONTMATTER ---
name: haro-docs
description: Quản lý và tạo cấu trúc tài liệu dự án theo mô hình Atomic
Content Blocks. Kích hoạt khi user muốn khởi tạo cấu trúc tài liệu cho dự án mới,
tổ chức tài liệu đang tồn tại, tổng hợp tài liệu hoàn chỉnh (BRD, PRD,
SAD, FSD...), review phản biện một vấn đề/file qua subagent, hoặc quản lý bộ nhớ
kiến thức project qua knowledge (ingest, index, clean, delete). Gõ /haro-docs không tham số để quét
dự án và chọn thao tác tiếp theo.

================================================================================
1. TỔNG QUAN
================================================================================

`haro-docs` tổ chức tài liệu dưới dạng **Atomic Content Blocks (Khối Nội dung
Nguyên tử)**: mỗi mục nhỏ là một file markdown riêng biệt, viết đúng một lần
(Single Source of Truth), sau đó lắp ghép thành tài liệu hoàn chỉnh (BRD, PRD,
SAD, FSD...).

Điểm mạnh:
- **Chuẩn hóa:** mọi dự án có cấu trúc tài liệu giống nhau, dễ đối chiếu chất lượng.
- **Nguyên tử:** mỗi block là một đối tượng riêng — dễ phân công, theo dõi trạng
  thái, quản lý phiên bản.
- **Linh hoạt:** tài liệu đầu ra chỉ là các "View" được tổng hợp từ cùng tập block
  gốc theo **Aggregation Matrix** (Mục 7).
- **Bộ nhớ kiến thức:** fact của project (business, technical, team...) lưu thành
  file nhỏ theo domain dưới `.haro-docs/knowledge/` và load chọn lọc như RAG.
- **Hai trạng thái:** mọi file docs là `UPDATING` (đang làm, chỉ tham khảo) hoặc
  `RELEASED` (đã chốt, phải chuẩn). Trạng thái chỉ nằm trong
  `.haro-docs/config/status.yaml` — file nội dung không gắn trạng thái.

================================================================================
1.1 KNOWLEDGE NHƯ RAG CHỌN LỌC (không cần vector DB)
================================================================================

Vì không có vector search, knowledge được tổ chức để truy xuất qua index + frontmatter:

- Mỗi fact nằm trong file topic đặt tên theo domain: `business-*.md`,
  `technical-*.md`, `team-*.md`, `common-*.md`, `security-*.md`... Một domain giữ
  1-3 file topic; mỗi file topic gom toàn bộ fact cùng chủ đề dưới các heading
  (không tạo file lẻ cho từng fact).
- Mỗi file topic có frontmatter YAML làm định danh máy đọc:
  `domain / tags / summary / updated`.
- `.haro-docs/knowledge/index.yaml` là nguồn tra duy nhất: mỗi file một entry
  `file | domain | tags | summary | updated | facts | state`. Agent chỉ đọc
  `index.yaml` (nhỏ) để quyết định file nào cần load cho task hiện tại, rồi chỉ
  load những file đó. Không load toàn bộ `knowledge/` mặc định. Không bao giờ
  ghi `index.yaml` bằng tay — file này do `--ingest` và `--index` sinh ra từ
  frontmatter.
- Dùng `index.yaml` trước mọi lượt `init`, `generate` cần context:
  đọc `index.yaml`, chọn entry có domain/tags khớp task (vd business cho BRD,
  technical cho SAD), chỉ load file khớp. Knowledge thắng default khi xung đột.

================================================================================
1.2 TRẠNG THÁI 2-STATE
================================================================================

- `UPDATING` (đang làm) = **nên tham khảo**: đọc lấy bối cảnh, không coi là sự
  thật, không ghép vào deliverable.
- `RELEASED` (đã chốt) = **phải chuẩn**: file sinh sau tuân thủ tuyệt đối, xung
  đột thì dừng và hỏi; chỉ `RELEASED` mới được ghép vào `10-deliverables/`,
  mới được dùng làm tiền đề/bằng chứng.
- Nguồn duy nhất: `.haro-docs/config/status.yaml`. Path nào vắng trong map thì tính là
  `UPDATING`. `generate` không bao giờ ghi vào file `RELEASED`.

================================================================================
2. WORKSPACE `.haro-docs/`
================================================================================

Skill lưu toàn bộ cấu hình và trạng thái vào `.haro-docs/` tại gốc dự án.
File YAML là nguồn duy nhất cho mọi tra cứu của agent; file Markdown dưới
`knowledge/`, `elicitation/`, `reviews/` là payload nội dung có frontmatter YAML.

.haro-docs/
├── config/
│   ├── project.yaml     # hồ sơ: loại, audience, doc-root, ngôn ngữ, version
│   ├── schema.yaml      # cây thư mục chuẩn + ma trận tổng hợp
│   ├── agents.yaml      # registry reviewer
│   └── status.yaml      # trạng thái docs: UPDATING | RELEASED
├── agents/              # bản copy agent của project (<id>.md + index.yaml)
├── knowledge/           # file topic (business-*, technical-*, team-*, common-*.md + index.yaml)
├── elicitation/         # Q&A tạm (<sanitized-path>.md + index.yaml)
└── reviews/             # báo cáo (RR-*.md + index.yaml)

> QUAN TRỌNG: `config/project.yaml` ghi rõ **doc-root** — vị trí lưu tài liệu do
> user chọn khi chạy `init`. Mọi lệnh (generate, knowledge) phải
> đọc config này trước khi thao tác. Tuyệt đối không suy đoán doc-root.

> THỨ TỰ ĐỌC CHUẨN (mọi lệnh): `config/project.yaml` → `config/schema.yaml`
> → `config/status.yaml` → `knowledge/index.yaml` (đọc index trước, không đọc payload) →
> chỉ load file payload khớp. Knowledge là ground truth khi xung đột với default quét được.
> Agent resolve qua `config/agents.yaml` + `agents/index.yaml` khi review/config cần.

> CẤU HÌNH NGÔN NGỮ: `config/project.yaml` cũng ghi **ngôn ngữ trả lời**
> (`language.response`) và **ngôn ngữ tài liệu** (`language.documentation`). Đây
> là nguồn sự thật duy nhất cho mọi quyết định giao tiếp và nội dung — xem Mục 9.
> Nếu trống hoặc thiếu, phải hỏi user trước khi chạy lệnh nào.

================================================================================
QUY TẮC TRÌNH BÀY — CHAT TRƯỚC, PICKER SAU (mọi lệnh)
================================================================================

1. Mọi nội dung (nhận định, outline A/B, preview ingest, synthesis review,
   dashboard) render **đầy đủ trong chat trước**.
2. Picker chỉ chứa **option lựa chọn** — nhãn ngắn (≤1 dòng, trỏ "xem chi tiết ở trên").
   Không bao giờ nén nội dung vào option để tiết kiệm context.
3. Thứ tự bắt buộc: message chat trước, **rồi mới** gọi picker — không gộp chung.
4. Mọi option dùng ngôn ngữ giao tiếp (`language.response`): tên gọi thường + hậu quả
   1 dòng. Token nội bộ (`UPDATING/RELEASED`, `unsure/defer/skip`, `save/skip`,
   `keep/remove`, `yes/no`) chỉ đứng trong ngoặc, không bao giờ làm nhãn trần.
5. Mọi picker khai báo mode: `single` mặc định; `multiple` chỉ cho chọn reviewer và
   hàng đợi file (chạy lần lượt theo thứ tự đã chọn; `dừng` kết thúc bất cứ lúc nào).

================================================================================
3. LỆNH `/haro-docs` (không tham số) - INDEX + FALLBACK (= `/` + sai lệnh về đây)
================================================================================

Khi user chạy `/haro-docs` không tham số, gọi `help` / `--help` / `-h`, hoặc tham số
không khớp lệnh nào, KHÔNG thực thi workflow. Hiện index: giới thiệu ngắn + bảng lệnh +
chọn thao tác (y như router: sai đường thì về `/`):

1. **Giới thiệu (chat, 3-4 dòng)** — haro-docs tổ chức docs theo Atomic Content Blocks
   (mỗi mục 1 file, viết 1 lần) rồi ghép thành BRD/PRD/SAD/FSD; mọi workflow lệnh nằm ở file
   riêng; trạng thái docs nằm ở `.haro-docs/`.
2. **Tóm tắt lệnh:** render bảng Command index trong `SKILL.md` (kèm ví dụ). Không nhân bản
   bảng thứ hai ở đây.
3. **Check nhẹ (1 lần đọc):** `.haro-docs/config/project.yaml` tồn tại → `Đã init tại <docroot>`;
   không thì → `Chưa init — chạy init trước`. Đọc sâu hiện trạng là việc của `/haro-docs init`
   (chạy lại lúc nào cũng được).
4. **Popup chọn thao tác** — hỏi làm gì tiếp (Mode: single; picker nếu có, không thì list
   đánh số): liệt kê 6 lệnh (`init`, `generate`, `review`, `knowledge`, `config`, `dừng`),
   mỗi lệnh 1 dòng khi nào dùng. Chưa init thì gợi ý sẵn `init`. Chốt rồi đọc workflow file
   của lệnh đó trước khi làm. KHÔNG tự chạy side-effect.

5. **Hiện Aggregation Matrix rút gọn** - BRD/PRD/SAD/FSD từ Mục 7.
6. **Không tạo file, không ghi file.** Nếu token đầu không khớp (vd `/haro-docs foo`), prefix
   `Unknown command 'foo'. Valid: init, generate, review, knowledge, knowledge --ingest, knowledge --index, knowledge --clean, knowledge --delete, config.`
   và gợi ý gần đúng. Alias `help`, `--help`, `-h` cũng hiện dashboard. So khớp
   case-insensitive.

================================================================================
4. LỆNH `/haro-docs knowledge` - BỘ NHỚ KIẾN THỨC (RAG CHỌN LỌC)
================================================================================

File kiến thức là fact chuẩn mà agent phải nhớ và tuân theo. Lưu thành file topic
theo domain để load chọn lọc mà không cần đọc toàn bộ.

### Lưu trữ

.haro-docs/knowledge/
├── index.yaml           # nguồn tra duy nhất — do --ingest/--index sinh, không ghi tay
├── business-*.md        # file topic có frontmatter (domain/tags/summary/updated)
├── technical-*.md
├── team-*.md
├── common-*.md
└── security-*.md

Mỗi file topic có frontmatter:

---
domain: business
tags: [team, stid]
summary: "STID là công ty, PM là Hảo"
updated: "YYYY-MM-DD"
---

Mỗi entry `index.yaml`:

  - file: "business-team.md"
    domain: "business"
    tags: [team, stid, pm]
    summary: "STID là công ty, PM là Hảo, member Hảo/Vu/Dai"
    updated: "YYYY-MM-DD"
    facts: 3
    state: active

Domain: `business`, `technical`, `team`, `common`, `security`, `quality`,
`operations`, `guides` - chọn gần nhất. Một domain giữ 1-3 file topic; fact mới
cùng chủ đề thì append vào file topic khớp nhất thay vì tạo file mới.

### Load chọn lọc (RAG không vector DB)

Trước mọi lượt `init`, `generate` cần context:

1. Đọc `knowledge/index.yaml` nếu tồn tại (nhỏ, luôn đọc).
2. Chỉ chọn entry có `state: active` và `domain`/`tags`/`summary` khớp task hiện tại
   (vd `business` cho BRD/Proposal, `technical`+`architecture` cho SAD/FSD,
   `team` cho task liên quan con người).
3. Chỉ load file knowledge khớp. KHÔNG load toàn bộ `knowledge/`.

Knowledge là ground truth: khi knowledge xung đột với code/README scan, ưu tiên
knowledge.

### Hub (không subcommand)

`/haro-docs knowledge` không subcommand thì mở picker (Mode: single; picker tool nếu có,
không thì list đánh số) — cùng pattern hub với `/haro-docs config`:

1. `Xem danh sách (list)` — xem toàn bộ fact trong kho kèm UID (read-only, xem bảng dưới)
2. `Nạp nội dung (ingest)` — gọi trần thì gợi ý fact ứng viên từ discussion đang có + nhập tay;
   gọi kèm nội dung thì chạy thẳng flow dưới đây
3. `Dựng index (index)` — sinh index + compact file nhỏ
4. `Dọn bộ nhớ cũ (clean)` — dọn stale (confirm từng dòng)
5. `Xóa fact (delete)` — xóa 1 fact đã ingest theo UID; gọi trần thì mở picker fact (single)

Gọi kèm flag/nội dung (`knowledge --ingest [<nội dung>]`, `--index`, `--clean`, `--delete [<uid>]`)
thì bỏ qua picker, chạy thẳng nhánh đó. Xong nhánh thì hỏi `về hub / dừng`.

### Subcommands

| Subcommand | Hành vi |
|------------|---------|
| `knowledge --ingest [<nội dung>]` | **Phân tích -> confirm -> lưu.** Gọi trần (gián tiếp): quét discussion hiện tại tìm fact project chưa có trong entry `active`, đề xuất 2-3 ứng viên + option nhập tay; chốt/chọn rồi chạy tiếp như trực tiếp. Gọi kèm nội dung (trực tiếp): parse text, tách fact riêng, viết lại mỗi fact thành câu chuẩn (văn current-state Mục 9), tìm file topic khớp cho mỗi fact (hoặc đặt tên file topic mới khi chưa có chủ đề khớp). So với
entry `active` hiện có trước; mâu thuẫn thì thêm khối `Mâu thuẫn: cũ A ↔ mới B` vào preview,
chỉ lưu khi confirm rõ từng mâu thuẫn (giữ-cả-hai / thay-thế / bỏ-mới). Rồi hiện preview bảng `file \| nội dung chuẩn` + entry index mới. Hỏi `Confirm? (yes / edit <sửa>)`. Chỉ khi `yes` (hoặc sau `edit` và yes lại) mới ghi file topic và ghi entry mới vào `index.yaml`. Mỗi fact mới cấp UID tiếp theo (`kb-NNNN` = max+1), ghi dạng block `<!-- <uid> -->` + câu fact; set `fact_ids` (+`facts` count; tăng cả hai khi append). Deduplicate trước: fact đã tồn tại thì báo kèm UID, không ghi trùng. |
| `knowledge` (= `list`, hub option 1) | **Liệt kê** (không tham số). Đọc `index.yaml` và render từng file: file \| domain \| fact dạng `uid: summary 1 dòng` \| updated, cộng số file. Read-only. |
| `knowledge --index` | **Sinh index + compact.** Đọc frontmatter mọi `knowledge/*.md`, ghi `index.yaml` mới từ đó, rồi compact: gộp file topic cùng domain nhỏ hơn ~10 dòng, dedup câu trùng. UID đi theo block của nó; đếm lại `facts`/`fact_ids`. Báo `trước N file → sau M file`. Không cần confirm; chỉ báo kết quả. |
| `knowledge --clean` | **Xóa bộ nhớ cũ/không liên quan.** Quét `index.yaml` tìm ứng viên: `state: stale`, `updated` quá 90 ngày (hoặc `--older-than <Nd>`), summary không còn tham chiếu trong code/docs. Hiện bảng `file \| lý do \| keep/delete` và confirm **từng dòng**. Chỉ dòng confirm `delete` mới bị xóa; sau đó ghi `index.yaml` mới. Không bao giờ xóa khi chưa confirm từng dòng. |
| `knowledge --delete [<uid>]` | **Xóa 1 fact đã ingest.** Có UID: tìm fact, hiện fact + file, confirm 1 lần rồi xóa block khỏi file; cập nhật `fact_ids`/`facts`/`updated`; file rỗng thì xóa file + entry; báo kết quả. Gọi trần: mở picker fact (single) thay vì hỏi UID. Không bao giờ xóa khi chưa confirm. |

Unknown subcommand cho nhóm này -> `Unknown command 'X'. Valid: knowledge, knowledge --ingest, knowledge --index, knowledge --clean, knowledge --delete.` rồi hiện bảng. `help`/`--help`/`-h` cũng hiện.

### Ví dụ

```
/haro-docs knowledge --ingest STID là công ty tôi, tôi là PM, member gồm Hảo (tôi), Vu (Backend) và Dai (Frontend)
/haro-docs knowledge
/haro-docs knowledge --index
/haro-docs knowledge --clean
/haro-docs knowledge --delete kb-0007
```

================================================================================
5. LỆNH `/haro-docs init <mô tả dự án>`
================================================================================

Đọc hiện trạng project để quyết định tiếp theo — chạy lúc nào, mấy lần cũng được: project mới
thì khởi tạo full cấu trúc, đã init thì refresh (đọc lại + báo delta).

### 5.1 ĐỌC SÂU (chạy đầu mọi lượt, read-only trừ sync refresh)

1. **Quét sâu** — README (domain, tính năng chính), cây source + tín hiệu tech stack, ước lượng
   quy mô code, docs hiện có trong và ngoài doc-root, trạng thái `.haro-docs/` (project.yaml,
   schema.yaml, số file knowledge, config agents).
2. **Thực trạng docs** — nếu đã init: liệt kê cây thực tế dưới doc-root (mỗi folder 00-common →
   99-assets: tồn tại/thiếu, số file, breakdown UPDATING/RELEASED từ `config/status.yaml`; path vắng
   tính là UPDATING). Check index knowledge/reviews/elicitation + agents enabled.
3. **Tổng hợp trong chat trước** — **Project Note** (5–8 dòng: đã init?, doc-root, coverage %
   RELEASED, top-3 gap, tech stack, độ sâu knowledge) + **Nhận định của agent** (2–3 dòng: rủi ro
   lớn nhất, gap đáng lo nhất, nước đi đề xuất + lý do 1 dòng).
4. **Rẽ nhánh:**
   - Chưa init → sang quy trình fresh (§5.2 dưới đây).
   - Đã init → **chế độ refresh**: thêm file docs mới xuất hiện vào `config/status.yaml` thành
     `UPDATING` (lần ghi duy nhất; không xóa/sửa gì của user), báo delta (file mới, coverage đổi,
     gap còn mở), rồi gợi ý lệnh tiếp theo (`generate`, `review`, `knowledge --ingest`) qua picker
     (Mode: single) và đi tiếp lệnh được chọn sau khi đọc workflow file của nó.

### 5.2 QUY TRÌNH CHUẨN

1. **Quét dự án** — dùng lại deep read §5.1 ở trên (không quét lần hai); chỉ đào sâu chỗ §5.1
   còn trống, để tổng hợp bối cảnh: domain nghiệp vụ, tính năng chính, quy mô code, ràng buộc kỹ thuật.
1b. **Phân tích của agent** — trình bày `Tình hình (3-5 dòng từ scan) → Nhận định
   (rủi ro, docs nào ưu tiên, stack có gì đáng ngờ) → Đề xuất của tôi (deliverable nào
   trước + vì sao)` **trong chat trước**, rồi mới sang câu hỏi làm rõ. Bỏ các câu hỏi
   mà phân tích đã trả lời được.
2. **Hỏi chủ động để làm rõ** — đặt câu hỏi cho user kèm gợi ý dựa trên kết quả quét:
   - Mục tiêu sản phẩm/giải pháp (free-text)
   - Đối tượng tài liệu (multiple: kỹ sư / quản lý / khách hàng / ...)
   - Phạm vi (free-text) và độ sâu kỹ thuật (single: high-level | balanced | deep-dive)
   - Yêu cầu bảo mật/tuân thủ đặc thù (multiple + free-text, vd GDPR, ISO 27001, ...)
   - Các loại tài liệu đầu ra cần có (multiple: BRD / PRD / SAD / ...)
   - **Ngôn ngữ trả lời** — ngôn ngữ agent dùng khi hội thoại: `en` hoặc `vi`
     - **Ngôn ngữ tài liệu** — ngôn ngữ nội dung tài liệu: `en`, `vi`, hoặc
       `vi-en` (định nghĩa tại Mục 9)
3. **Hỏi vị trí lưu tài liệu (doc-root)** — user chọn (single):
   - `docs/` (thư mục tài liệu truyền thống), hoặc
   - `.haro-docs/docs/` (gói gọn trong workspace của skill)
3b. **Chốt quy ước (gọn 4-6 câu)** — quy tắc cố định không cần hỏi (nằm ở Mục 9 luật viết);
   chỉ hiện preview read-only. Chỉ hỏi quy ước đặc thù dự án dưới đây, đáp án ghi vào
   `config/project.yaml` (`conventions:`, `audience.technical_depth`, `deliverables`), kèm
   default suy từ scan:
   - Diagram tool (single) → `conventions.diagram_tool`: `mermaid | plantuml | drawio` (+ fallback image)
   - API spec format (single) → `conventions.api_format`: `openapi-yaml | md-table | both`
   - Tone & độ sâu (single) → `audience.technical_depth`: `high-level | balanced | deep-dive`
   - Người duyệt RELEASED (free-text) → `conventions.approver`: một tên/role, hoặc duyệt theo domain
   - Thuật ngữ khóa (free-text) → `conventions.locked_terms`: tên sản phẩm/thương hiệu giữ nguyên cách viết, hoặc `(none)`
   - Deliverable ưu tiên (multiple) → `deliverables`: BRD/PRD/SAD/... nào trước, hoặc `(all)`

   Mục nào bỏ trống thì dùng default đã ghi rõ.
3c. **Thiết lập agent (nhanh)** — chạy flow dùng chung ở Phụ lục 12: hiện bảng preset
   trong chat, tick chọn role (multiple), đặt tên từng con, chọn default, confirm rồi ghi.
   Bỏ qua thì không ghi gì — không tạo `config/agents.yaml`, và flow setup sẽ hiện lại khi
   lệnh nào đó cần agent.
4. **Xác nhận dàn ý** — trình bày cây thư mục + danh sách file cụ thể (đã gồm quy ước
   vừa chốt), chờ user duyệt. Nếu dự án đã có tài liệu nằm ngoài cây chuẩn, kèm luôn
   bảng đặt vị trí `old path → new path` trong bước này, chờ confirm từng dòng.
5. **Khởi tạo** — sau khi duyệt:
   - Tạo `.haro-docs/config/project.yaml` và `.haro-docs/config/schema.yaml`
     (từ template trong thư mục `templates/` của skill) với `version: 1`,
     bao gồm cả `language.response` và `language.documentation` đã chọn
   - Agent: nếu bước 3c đã setup xong, `config/agents.yaml` có sẵn — giữ nguyên. Nếu đã bỏ
     qua, không tạo gì: flow setup ở Phụ lục 12 sẽ hiện lại khi lệnh nào đó cần agent.
   - Tạo `.haro-docs/config/status.yaml` từ `templates/status.yaml`, liệt kê mọi file
     theo dàn ý với trạng thái `UPDATING`
   - Tạo `.haro-docs/knowledge/index.yaml` từ `templates/knowledge.yaml`
     với `entries: []` rỗng
   - Tạo `.haro-docs/reviews/index.yaml` từ `templates/reviews.yaml`
     với `entries: []` rỗng
   - Tạo `.haro-docs/elicitation/index.yaml` từ `templates/elicitation.yaml`
     với `entries: []` rỗng
   - Render `00-common/01-conventions.md` dạng view chỉ-đọc từ `config/project.yaml`
     (`conventions:`, `audience.technical_depth`, `deliverables`) với trạng thái RELEASED;
     tạo `02-references.md`, `03-abbreviations.md`,
     `04-glossary.md`, `05-traceability.md` dạng placeholder cho `generate` điền
     (trạng thái UPDATING)
   - Tạo cây thư mục theo dàn ý, mỗi thư mục có `README.md` mô tả phạm vi
   - Tạo README tổng quan tại doc-root theo outline ở Mục 8 (Doc-root README outline),
     điền cây và lộ trình đọc từ `config/schema.yaml` + `config/project.yaml`

6. LỆNH `/haro-docs generate` / `generate <file>` - XÂY DOCS (HỎI ĐÁP DẪN DẮT)
================================================================================

Xây tài liệu linh hoạt dựa trên thực trạng + vai trò bạn. Hai chế độ:

- `/haro-docs generate` — đề xuất 2-3 file tiếp theo để xây, dựa trên thực trạng.
  Bỏ qua toàn bộ `00-common` — `01-conventions.md` do `init` render từ project.yaml,
  `02-05` do `generate` tự điền; điểm bắt đầu viết là `01-overview`.
- `/haro-docs generate <file>` — tạo file chỉ định (vd `02-business/01-value-prop.md`
  hoặc `10-deliverables/01-BRD.md`). Nếu file đã `RELEASED`, báo
  `File is RELEASED (final)` kèm tóm tắt 1 dòng và gợi ý file đang mở tiếp theo —
  `generate` không bao giờ ghi vào file `RELEASED`.

### Thứ tự chuẩn

Thứ tự là `00-common -> 01-overview -> 02-business -> 03-features -> 04-architecture
-> 05-security -> 06-implementation -> 07-quality -> 08-operations -> 09-guides
-> 10-deliverables -> 99-assets` như trong `schema.yaml` và Mục 8. Trong mỗi folder,
file xếp theo prefix số. Thứ tự này là tham chiếu để hiểu tiền đề
(vd `01-overview` và `02-business` là tiền đề cho `04-architecture`). Nếu tất cả đã
`RELEASED`, trả `Tất cả đã hoàn thiện.`.

### Lưu elicitation

Q&A tạm lưu tại `.haro-docs/elicitation/<sanitized-path>.md` (vd
`02-business-01-value-prop.md`) với frontmatter (`target`, `updated`, `gaps`) để đỡ
context. Chỉ đọc khi cần trong `generate` — tìm file qua `.haro-docs/elicitation/index.yaml`
(mỗi file một entry: `target | file | updated | open_gaps`). Tạo file elicitation thì ghi
entry; xóa file thì xóa entry. Không bao giờ ghi index bằng tay. Sau khi xong file chính,
hỏi user giữ hay xóa file elicitation.

### Trạng thái

Nguồn duy nhất là `.haro-docs/config/status.yaml`. File docs không gắn trạng thái; path
vắng trong map tính là `UPDATING`:

- `UPDATING` — đang làm, chỉ tham khảo: đọc lấy bối cảnh, không coi là sự thật,
  không ghép vào deliverable.
- `RELEASED` — đã chốt, phải chuẩn: file sinh sau tuân thủ tuyệt đối; chỉ `RELEASED`
  mới ghép vào `10-deliverables/`; `generate` không bao giờ ghi vào file `RELEASED`.
- `00-common/02-references.md`, `03-abbreviations.md`, `04-glossary.md`,
  `05-traceability.md` là tham chiếu sống với trạng thái `UPDATING` nên `generate`
  append vào bất cứ lúc nào.

### QUY TRÌNH

1. **RAG chọn lọc** — đọc `knowledge/index.yaml` (nếu có), chọn entry có
   `state: active` và domain/tags khớp file đích (`business` cho BRD, `technical`+
   `architecture` cho SAD, `team` cho người), chỉ load file khớp. Đọc
   `.haro-docs/config/status.yaml`: file `RELEASED` trong phạm vi là ràng buộc cứng
   (xung đột thì dừng và hỏi), file `UPDATING` chỉ là bối cảnh.
1b. **Nhận định mở màn của agent** — từ RAG + status, trình bày 3-5 dòng trong chat
   (`Tình hình → Nhận định → Góc tiếp cận tôi đề xuất`) **trước** khi đề xuất file/câu hỏi.
   Khi file đích phụ thuộc tiền đề chưa xong, nói thẳng vì sao nên quay về tiền đề thay vì
   hỏi xuông.
2. **Đề xuất file theo thực trạng:**
    - Quét thực trạng từ `status.yaml`: file nào còn `UPDATING`, file nào
      `RELEASED`, `change-requests/CR-*.md` nào có. Dùng order chuẩn làm tham chiếu để hiểu
      tiền đề (vd `01-overview` và `02-business` là tiền đề cho `04-architecture`).
      Bỏ qua toàn bộ `00-common` (`01-conventions.md` là view render sẵn, `02-05` do
      generate tự điền); điểm bắt đầu viết là `01-overview`, không phải `00-common`.
   - Nếu `<file>` đã `RELEASED`: báo final và gợi ý file đang mở tiếp theo.
   - Nếu `<file>` còn `UPDATING`: coi như bạn muốn file đó, nhưng nếu nó phụ thuộc tiền đề chưa
     xong (vd nhắm `04-architecture` trong khi `01-overview/03-goals.md` còn trống),
     giải thích vì sao tiền đề quan trọng và hỏi `Bạn muốn tiếp tục file này hay
     chuyển sang tiền đề?`.
   - Nếu không có `<file>`: đề xuất **2-3 ứng viên** cho file tiếp theo, mỗi cái
     kèm lý do 1 dòng (vd `1. 01-overview/01-problem-statement.md — mục đích nền tảng
     còn trống; 2. 02-business/01-value-prop.md — business cần trước architecture`).
     Mode: multiple — các file được chọn thành hàng đợi, chạy full flow từng file theo thứ tự
     đã chọn; `dừng` kết thúc hàng đợi; chọn 1 file thì hành vi như thường. Để bạn chọn.
   - Khi đã chọn/chốt đích, đọc file lân cận cùng folder + glossary lấy context.
3. **Hỏi đáp dẫn dắt, được bỏ qua/để sau:**
   - Sinh **~5 câu hỏi** từ `domain file + thực trạng` (vd `02-business/*` ->
     market/pain/SLA/metrics; `04-architecture/*` -> flow/business rule/endpoint/schema/
     NFR/diagram). Diễn đạt mỗi câu bằng lời lẽ thường, ai cũng đánh giá được.
   - Mỗi câu chấp nhận bốn kiểu đáp: câu trả lời, `unsure` (chưa rõ), `defer` (để sau),
     hoặc `skip` (bỏ qua) — không ai bị ép đoán mò. Ghi từng câu kèm trạng thái
     (`answered | unsure | deferred | skipped`) vào mục `gaps:` của elicitation file.
     Câu `chưa rõ` thì gắn cờ, không bao giờ coi là căn cứ. Append Q&A vào elicitation file.
   - Phân tích field nào của file đích (theo schema) còn thiếu → hỏi tiếp 3-5 câu bổ sung,
     append, lặp đến khi đủ. Hỏi lại các câu `để sau` một lần vào cuối; câu nào vẫn để sau
     thì giữ làm gap mở.
   - **Phản biện bắt buộc** — khi câu trả lời mâu thuẫn knowledge / file RELEASED / bằng chứng
     quét, dừng và dùng đúng khung: `Bạn nói X → nhưng bằng chứng Y cho thấy Z → giữ X hay
     đổi? (giữ / đổi / bỏ qua câu này)`. Không bao giờ ghi lặng lẽ đáp mâu thuẫn. Đáp giữ lại
     mà mâu thuẫn thì ghi cờ `contested` trong elicitation, không lan vào doc chính.
4. **Đề xuất outline kèm đối sánh** — render full outline **trong chat trước**, rồi mới pick.
   Trình bày `Phương án A khuyến nghị (cấu trúc section + vì sao hợp) → Phương án B thay thế
   (cấu trúc khác + tradeoff 1 dòng mỗi bên)` → gap mở. Đánh dấu section phụ thuộc câu
   `chưa rõ`/`bỏ qua` là `[CHƯA XÁC NHẬN]` và liệt kê gap mở. Mode: single — picker chỉ có
   `Chọn A (khuyến nghị) / Chọn B (thay thế) / Sửa outline`, mỗi option ≤1 dòng (chi tiết đã
   nằm ở chat).
5. **Viết** — tạo file đích trong folder chuẩn (kebab-case + prefix số,
   Mục 9) bằng văn current-state first-version (Mục 9). Tuân thủ quy ước trong
   `config/project.yaml` (`conventions:`, `audience.technical_depth`;
   `00-common/01-conventions.md` chỉ là view chỉ-đọc của chúng);
   nếu conventions thiếu chỉ dẫn cho file này thì dùng default hợp lý và ghi chú 1 dòng,
   không ghi vào conventions. Ghi trạng thái mới vào `.haro-docs/config/status.yaml`
   (`UPDATING`). Nếu có fact mới, ghi vào `knowledge/` khi cần.
6. **Tự động điền 00-common** — ngay sau khi viết, quét nội dung mới để tìm
   thuật ngữ, viết tắt, reference chưa có trong `00-common/`. Append vào
   file tương ứng mà không cần lệnh khác:
   - Thuật ngữ mới → append vào `00-common/04-glossary.md` với định nghĩa 1 dòng
     suy từ context; nếu `vi-en` thì thêm gloss tiếng Anh.
   - Viết tắt mới → append vào `00-common/03-abbreviations.md`.
   - Reference ngoài mới → append vào `00-common/02-references.md`.
   Không cần confirm; chỉ ghi chú `Auto 00-common: +2 terms, +1 abbreviation.`
   trong reply. Deduplicate trước khi append.
7. **Dọn elicitation** — Mode: single. Hỏi với option `Giữ để tra cứu (keep)` / `Xóa file + entry index (remove)`. Khi `remove`, xóa file và entry của nó trong `elicitation/index.yaml`.
8. **Confirm & đánh trạng thái** — Mode: single. Hỏi với option `Chốt file (RELEASED) — file thành căn cứ cho các file sau` / `Để đang làm (UPDATING) — gap ở lại lượt sau`. Chỉ chọn `RELEASED` khi không còn gap chặn; còn gap thì giữ `UPDATING`, gap nằm lại
   elicitation file để lượt sau xử lý. Ghi trạng thái mới vào `.haro-docs/config/status.yaml`.
   File `RELEASED` thành căn cứ cho các lượt `generate` sau.
9. **Popup lệnh tiếp theo** — sau khi đánh trạng thái luôn hỏi làm gì tiếp (picker nếu
   có, không thì list đánh số). Đề xuất 2-3 ứng viên cụ thể theo thực trạng mới (tiền đề
   + gap), mỗi cái kèm lý do 1 dòng, cộng thêm `review <file vừa xong>` và `dừng`. Chờ
   user chọn; KHÔNG tự chạy.

| Ngôn ngữ           | Kỹ thuật (được phép tham chiếu schema, endpoint) | Nghiệp vụ thuần, không chi tiết kỹ thuật |
| Quy tắc SSOT       | Story link chéo sang use case để biết bối cảnh | Use case KHÔNG chứa chi tiết kỹ thuật |

Một use case thường được bóc tách thành nhiều user story; mỗi story đặt link ngược
về use case nguồn thay vì kể lại luồng.

Folder chưa cần dùng có thể giữ nguyên `README.md` và ghi chú ngắn
`> Out of scope for this project`.

9. QUY TẮC BIÊN SOẠN
================================================================================

1. **Single Source of Truth:** mỗi nội dung chỉ viết một lần tại một file duy nhất;
   tài liệu tổng hợp chỉ ghép, không sao chép nội dung.
2. **Cấu hình ngôn ngữ** — đọc từ `project.yaml`
   (`language.response`, `language.documentation`):
   - **Phản hồi hội thoại** (câu hỏi làm rõ, Q&A elicitation, đề xuất dàn ý...)
     dùng `language.response`.
   - **Nội dung tài liệu** dùng `language.documentation`, định nghĩa:

     | Chế độ | Định nghĩa | Ví dụ |
     |--------|-----------|-------|
     | `en`   | Thuần tiếng Anh | — |
     | `vi`   | Thuần Việt; chỉ giữ nguyên tiếng Anh cho TÊN RIÊNG / tên sản phẩm / công nghệ không có bản dịch (code, Java, PostgreSQL, REST API...) | "Hệ thống chạy trên PostgreSQL" |
     | `vi-en`| Tiếng Việt kèm chú thích tiếng Anh trong ngoặc ở LẦN DÙNG ĐẦU của mỗi thuật ngữ chuyên ngành; đăng ký các thuật ngữ đó vào `glossary.md` | "Cơ sở dữ liệu (database) lưu trữ hồ sơ" |

      Phân biệt hai chế độ cuối: `vi` giữ từ tiếng Anh vì KHÔNG CÓ từ Việt tương
      đương; `vi-en` chủ động kèm gốc tiếng Anh để DẠY THUẬT NGỮ, giúp người đọc
      tra cứu thêm.

      **`vi` chi tiết — tiếng Việt thuần.** Tiếng Anh chỉ xuất hiện ở chỗ tiếng Việt
      không có từ: tên riêng, tên sản phẩm/công nghệ, identifier trong code
      (PostgreSQL, REST API, `userId`...). Không dịch tên riêng ra tiếng Việt, không
      chú thích Anh trong ngoặc.
      - Đúng: "Hệ thống chạy trên PostgreSQL và expose REST API."
      - Sai: "Cơ sở dữ liệu (database) lưu trữ hồ sơ." — chú thích trong ngoặc là việc
        của `vi-en`; ở `vi` chỉ viết "Cơ sở dữ liệu".

      **`vi-en` chi tiết — tiếng Việt có dạy thuật ngữ.** LẦN ĐẦU gặp mỗi thuật ngữ
      chuyên ngành/domain thì kèm gốc tiếng Anh trong ngoặc và đăng ký vào `glossary.md`;
      các lần sau chỉ dùng tiếng Việt.
      - Lần đầu: "Cơ sở dữ liệu (database) lưu trữ hồ sơ." Lần sau: "Cơ sở dữ liệu
        được backup hằng ngày."
      - Chỉ gloss thuật ngữ chuyên ngành/domain (database, deployment, stakeholder...).
        KHÔNG gloss từ thông thường — "Hệ thống (system) chạy (run)" là nhiễu. KHÔNG
        gloss tên riêng — giữ trần như `vi`.

      **Chọn khi nào:** độc giả chỉ đọc tiếng Việt → `vi`; độc giả cần tra cứu tài liệu
      Anh sau này → `vi-en` để tài liệu dạy từ ngay lần đầu.
   - **Fallback:** nếu cấu hình ngôn ngữ trống hoặc thiếu → PHẢI hỏi user quyết
     định trước khi chạy lệnh nào. Tuyệt đối không tự suy đoán mặc định.
3. **Ghi trạng thái hiện tại như phiên bản đầu tiên:** khi tạo block/tài liệu, luôn viết
   nội dung cuối cùng như thể viết từ đầu hôm nay. Tài liệu mô tả sự vật ĐANG NHƯ THẾ NÀO.
   TUYỆT ĐỐI không dùng văn change-log trong thân tài liệu: "đã bổ sung...",
   "trước đây...", "không còn áp dụng...", "previous version". Không nhúng lịch sử
   phiên bản, ghi chú thay đổi hay mục "có gì mới" vào bất kỳ đâu — việc kiểm soát
   phiên bản do **git đảm nhiệm**.

   | Sai (trong nội dung) | Đúng |
   |----------------------|------|
   | "Đã bổ sung tính năng thanh toán vào module hóa đơn." | "Module hóa đơn bao gồm tính năng thanh toán..." |
   | "Phần báo cáo cũ đã bị loại bỏ ở phiên bản này." | *(đơn giản vắng mặt, không để lại dấu vết)* |

4. **Không trùng lặp:** kiểm tra glossary trước khi định nghĩa thuật ngữ mới.
5. **Tên file:** kebab-case kèm tiền tố số thể hiện thứ tự đọc — ví dụ
   `01-problem-statement.md`.
6. **Hình ảnh/sơ đồ:** lưu tại `99-assets/`, tham chiếu bằng đường dẫn tương đối;
   không nhúng base64 inline.
7. **Vòng đời block:** mỗi block là `UPDATING` (đang làm, chỉ tham khảo) hoặc
   `RELEASED` (đã chốt, phải chuẩn), quản lý tại `.haro-docs/config/status.yaml`;
   chỉ block `RELEASED` được đem vào tài liệu tổng hợp.
8. **README con:** mọi thư mục phải có `README.md` mô tả phạm vi và danh sách file.
9. **Cộng sự chủ động (áp mọi lệnh):** trình bày nhận định của mình trước khi hỏi;
mọi đề xuất kèm ít nhất một phương án thay thế + tradeoff 1 dòng mỗi bên; khi input
của user mâu thuẫn bằng chứng (knowledge, file RELEASED, kết quả quét), **dừng và
phản biện** theo khung `Bạn nói X → nhưng bằng chứng Y cho thấy Z → giữ X hay đổi?
(giữ / đổi / bỏ qua câu này)` trước khi ghi bất cứ gì. User quyết cuối — trên đầy
đủ thông tin.
10. **File generated là view chỉ-đọc:** `00-common/01-conventions.md` (render từ
`config/project.yaml`), `05-traceability.md` và README doc-root do đúng lệnh chủ quản
sinh ra — không bao giờ viết tay, không dùng làm nguồn viết.

10. LỆNH `/haro-docs review <chủ đề|file>` - REVIEW PHẢN BIỆN QUA SUBAGENT
================================================================================

Nghiên cứu, phân tích và đánh giá khách quan một vấn đề, ý tưởng hoặc file docs
bằng tư duy phản biện và logic. Skill điều phối subagent review ("đệ tử"), rồi tổng
hợp các báo cáo thành một verdict + đề xuất tiếp theo. **Chỉ-đọc với docs**: file
được review không bao giờ bị ghi; chỉ ghi báo cáo mới vào `.haro-docs/reviews/` khi đã hỏi.

CÚ PHÁP:

/haro-docs review Có nên dùng microservices cho dự án này?
/haro-docs review 04-architecture/02-components.md
/haro-docs review --no-agents Mô hình pricing hiện tại có lỗ hổng

QUY TRÌNH:

1. **Parse đích + load context (RAG chọn lọc)** — đọc `knowledge/index.yaml` (nếu có),
   chỉ load entry có `state: active` và domain/tags khớp chủ đề. Đọc
   `.haro-docs/config/status.yaml`: đích `RELEASED` được tính là căn cứ mức bằng chứng;
   đích `UPDATING` chỉ tính là bối cảnh (finding về nó là góp ý draft, không phải
   verdict trên căn cứ chốt). Nếu đích là đường dẫn docs: đọc file đó +
   file lân cận cùng folder + glossary. Nếu là text tự do: quét nhẹ repo + doc-root tìm
   bằng chứng liên quan. Nêu rõ `sources: ...` để reviewer trích dẫn được.
2. **Đảm bảo agent rồi chốt reviewer:** khi `.haro-docs/config/agents.yaml` thiếu hoặc
   không có entry enabled nào, chạy flow setup dùng chung ở Phụ lục 12 trước (bỏ qua =
   dừng review: báo `No reviewers configured` rồi kết thúc). Rồi mới chốt reviewer:
   - Hiện agents đang enabled (`id | invoke | role`), cho user multi-select (picker nếu
     có, không thì list đánh số). Mode: multiple. Pre-select `default_reviewer`. Mặc định là **1 critic**;
     chỉ chạy multi-agent khi user chọn 2+ agents hoặc chủ đề cần cả research + phản biện.
   - Cờ `--no-agents` ép chạy single inline critic, bỏ qua config.
   - Nếu runtime không có cơ chế subagent (không có Task tool): **fallback inline** — chạy
     tuần tự từng reviewer trong context hiện tại, gắn nhãn `Reviewer <id> (inline
     fallback)`, rồi tổng hợp. Không fail chỉ vì thiếu subagent.
3. **Điều phối reviewer** — mỗi reviewer nhận: nội dung chủ đề/file, tóm tắt context, và
   persona của nó: bản copy project (`.haro-docs/agents/<file>`, tìm qua `.haro-docs/agents/index.yaml`)
   khi có, không thì `role + prompt` trong entry `config/agents.yaml`. Rẽ theo `invoke`: `task` →
   Task tool với `subagent_type: <type>`; `command` → nhờ runtime chạy `<command>` với cùng payload
   (runtime không hỗ trợ thì fallback inline + ghi chú trong synthesis); `inline` → chạy trong context.
   Bắt buộc trả về cấu trúc:
   - `findings:` list (nhận định → bằng chứng `file:line` hoặc `knowledge/<file>`)
   - `counter-arguments:` góc nhìn đối lập mạnh nhất
   - `verdict:` agree | conditionally-agree | disagree + lý do
   - `confidence:` high/medium/low cho từng finding
   - `open questions:` bằng chứng nào còn thiếu
   Chạy song song các agents khi runtime hỗ trợ.
4. **Tổng hợp (skill làm, không phải subagent)** — đối chiếu các báo cáo thành:
   - `Consensus:` điểm mọi reviewer đồng ý
   - `Conflicts:` điểm bất đồng (ai nói gì)
   - `Missing evidence:` cái gì sẽ chốt được mâu thuẫn
   - `Overall verdict:` agree | conditionally-agree | disagree + rationale 3-5 dòng
   - `Risks & alternatives:` list ngắn
   Trả lời bằng `language.response`. Khách quan: báo cáo trung thực bất đồng, không giấu.
5. **Lưu báo cáo (phải hỏi trước)** — Mode: single. Hỏi với option `Lưu báo cáo (save) — ghi vào reviews/ + index` / `Bỏ qua (skip)`. Nếu `save`, ghi `.haro-docs/reviews/RR-YYYYMMDD-HHmmss-<slug>.md` với
   frontmatter (`topic, verdict, reviewers, date, sources`) + synthesis + tóm tắt từng
   reviewer. Không ghi khi chưa hỏi.
6. **Popup tiếp theo** — sau synthesis luôn đề xuất follow-up (Mode: single; picker nếu có): vd
   `generate <file liên quan>`, `knowledge --ingest <fact mới lộ ra>`, `review lại với thêm bằng
   chứng`, `dừng`. Chờ pick; KHÔNG tự chạy.

VÍ DỤ:

/haro-docs review Có nên dùng microservices cho dự án này?
/haro-docs review 05-security/01-threat-model.md
/haro-docs review --no-agents SLA hiện tại có thực tế không?

11. LỆNH `/haro-docs config` - HUB CẤU HÌNH (agents | conventions | language)
================================================================================

Hub tập trung cho cấu hình skill. Ba nhánh, doc-root nằm trong `project.yaml`
(được chọn lúc `init`).

### 11.1 HUB (không tham số)

/haro-docs config               → picker hub (chỉ-đọc cho đến khi chọn nhánh)
/haro-docs config agents        → vào thẳng §11.2
/haro-docs config conventions   → vào thẳng §11.3
/haro-docs config language      → vào thẳng §11.4

QUY TRÌNH:

1. Đọc state: `agents.yaml` (có? N enabled, default?), `conventions:` + `audience.technical_depth`
   + `deliverables` từ `config/project.yaml` (hoặc `missing`),
   `language.response/documentation` từ `project.yaml`.
2. Hiện picker (Mode: single; picker tool nếu có, không thì list đánh số), mỗi dòng kèm 1 dòng trạng thái:
   - `1. agents — subagent review (N enabled, default: <id>)`
   - `2. conventions — quy ước đặc thù (diagram, API format, tone, approver...)`
   - `3. language — ngôn ngữ trả lời + ngôn ngữ tài liệu`
3. Vào nhánh được chọn. Xong nhánh thì hỏi `về hub / dừng`. Arg lạ →
   `Unknown command 'config X'. Valid: agents, conventions, language.` rồi hiện hub.

### 11.2 NHÁNH: agents - QUẢN LÝ SUBAGENT REVIEW

Quản lý cấu hình `.haro-docs/config/agents.yaml`:

1. Thiếu file hoặc không có entry enabled nào thì chạy flow setup dùng chung ở Phụ lục 12
   trước (nó list preset từ `templates/agents.yaml`).
2. Có rồi thì liệt kê `id | invoke | type/command | role | enabled | default?` (file/model
   từng id tra qua `.haro-docs/agents/index.yaml`).
3. Cho chọn thao tác (Mode: single; picker nếu có, không thì list số): `thêm từ mẫu | thêm custom (trắng) |
   gắn sẵn có | chỉnh model | bật / tắt | đặt default_reviewer | export sang IDE | reset từ template (confirm trước)`.
   - thêm từ mẫu: chọn preset trong registry → đặt tên (lowercase-hyphen, duy nhất) → invoke
     (default theo preset) → copy file mẫu vào `.haro-docs/agents/` khi thiếu → confirm rồi ghi index + registry.
   - thêm custom (trắng): đặt tên → tạo `.haro-docs/agents/<tên>.md` từ `agents/_blank.md`
     để user tự điền → confirm rồi ghi.
   - gắn sẵn có: chọn nguồn — Task runtime type (catalog: sub_reviewer, sub_qc, sub_sec, sub_ba,
     sub_e2e, sub_uiux, sub_data, sub_arch, explore), hoặc `@command` (gõ tay, hoặc pick từ
     `.claude/agents/*.md` / `.agents/**` khi tìm thấy), hoặc file project có sẵn → đặt tên → confirm.
   - chỉnh model: chỉ sửa dòng `model:` trong frontmatter bản copy project; confirm trước khi ghi.
   - export sang IDE: copy `.haro-docs/agents/<id>.md` sang `.claude/agents/` (Claude Code) hoặc
     `.agents/`; confirm đích trước; không tự ghi ra ngoài.
4. Sau khi ghi, render lại list và nhắc `/haro-docs review` sẽ offer các agents này để chọn.

### 11.3 NHÁNH: conventions - ĐẶT QUY ƯỚC ĐẶC THÙ

Đặt mapping `conventions:` trong `.haro-docs/config/project.yaml` (cùng `audience.technical_depth`
và `deliverables` khi liên quan):

1. Hiện giá trị hiện tại dạng bảng `key | giá trị` (`diagram_tool | api_format | tone ← audience.technical_depth | approver | locked_terms | deliverables`); luật cố định nằm ở Mục 9 luật viết, chỉ hiện tiêu đề khi được hỏi.
2. Cho đặt từng key (Mode: single; picker nếu có, không thì list số), mỗi key kèm default suy từ scan.
3. Confirm trước mọi ghi file. Sau khi ghi, render lại view `00-common/01-conventions.md` từ yaml
   để không bao giờ lệch.
4. Sau lưu, gợi ý `review` cho các file RELEASED mà quy ước mới chạm tới — chỉ gợi ý
   lệnh `review`, `config` không bao giờ ghi vào file docs.

### 11.4 NHÁNH: language - NGÔN NGỮ TRẢ LỜI + TÀI LIỆU

1. Hiện `language.response` + `language.documentation` từ `.haro-docs/config/project.yaml`
   (kèm định nghĩa `vi` vs `vi-en` ở Mục 9).
2. Cho đặt với option `en | vi | vi-en` tùy mục; confirm trước khi ghi vào `project.yaml`.

12. PHỤ LỤC: FLOW SETUP AGENT DÙNG CHUNG (init 3c / review / config agents)
================================================================================

Chạy khi agent chưa thiết lập: thiếu `.haro-docs/config/agents.yaml` hoặc không có entry
enabled nào. Nội dung đầy đủ ở `shared/agents-setup.md` — tóm tắt cho người đọc:

1. Hiện bảng preset trong chat trước (tên | lăng kính | chạy bằng gì | gợi ý on/off):
   critic, researcher (gợi ý on); po, pm, ba, arch, sec, qc, e2e, reviewer, docs, data,
   lead, expert (gợi ý off); custom (trắng).
2. Picker multiple: tick role cần dùng. Không chọn gì (hoặc `dừng`) = bỏ qua: không ghi
   file nào, flow sẽ hiện lại khi lệnh khác cần agent.
3. Đặt tên từng con (mặc định = id mẫu; lowercase-hyphen, duy nhất; trùng thì hỏi lại).
4. Invoke theo default preset (task dùng `type` = stem file, khỏi gõ; command hỏi `@name`).
5. Chọn default_reviewer (single).
6. Confirm bảng `tên | mẫu | invoke | default?` (`proceed / edit`) rồi ghi: copy file mẫu vào
   `.haro-docs/agents/` (chỉ file còn thiếu, không ghi đè file user đã sửa), ghi
   `.haro-docs/agents/index.yaml` + `.haro-docs/config/agents.yaml`. Báo kết quả rồi về
   luồng gọi.
